# 世界基座 07：因果机制注册表（声明单一事实源）

## 1. 定位

本篇对应 issue #46 的 P1 交付：**机制注册表**（`backend/ascend/causal/`）。
它把[第一阶段实施定义](../第一阶段实施定义.md) §2 的声明契约变成可执行的数据结构：
声明不再是研究侧的平行文档，而是生产求值的唯一事实源。

```
生产机制注册表 MechanismRegistry（NodeSpec / MechanismSpec / 参数 / 外生源）
   ├──→ 生产求值（derive.py 等委托 evaluate，输入/输出按声明值域 fail-closed 校验）
   ├──→ 声明快照（确定性序列化，declaration hash 稳定）
   │        → research/equations/equations.json（自动生成，禁止手改）
   │        → gen_lean.py → GenDeclarationData.lean → Lean 对账定理
   └──→ 构造期验收：C0 声明完整性 + C1 结构最小性（见证实测重跑）
```

后续 P2 干预执行器、P3 研究 trace、P4 完整存档均以本注册表为挂载点。

## 2. 数据契约

全部规范类 `frozen dataclass`（`backend/ascend/causal/spec.py`），
注册表构造后不可变（属性赋值抛 `AttributeError`）。

| 类 | 职责 | 对应实施定义条款 |
| --- | --- | --- |
| `NodeSpec` | 内生变量模板：角色（机制状态/持久状态/读出量）、实例域、值域（类型/单位/界/量化/缺失）、状态归属与重建规则、更新微步与携带规则、干预/追踪/观测权限、误差元数据 | §2 表格 14 项 |
| `ParentSpec` | 结构父模板：lag、源微步、空间偏移、实体关系、聚合/广播/边界算子、guard、Lipschitz 常数、分析角色 | §5 空间声明 |
| `ParameterSpec` | 环境参数：类型/单位/界/当前值/版本/可否环境干预/来源 | §2 参数条款 |
| `ExogenousSourceSpec` | 原始随机源：分布、抽取微步、实例索引、地址模板、共享关系 | §6 随机源声明 |
| `MechanismSpec` | 可执行方程：函数 + 显式父/参数/随机绑定 + 边界情况 + C1 见证 | §2 结构方程 |
| `DependencyWitness` | C1 功能依赖见证：固定上下文，仅替换一个父值，输出必须改变 | 04 篇 C1 |

**关键语义**：

- **执行角色与解释标签分离**：求值边一律 `structural`；边是否为物理反推
  （如海面温度→纬度代理）只是元数据 `analysis_role`，不再用旧 `inverse`
  role 标记生产依赖（旧约定把执行边标成 inverse 是 #46 指出的漂移之一）。
- **fail-closed**：C0 任何字段只能显式填写或由已文档化规则唯一推出；
  `evaluate` 拒绝多余/缺失父值、越出声明值域、bool 冒充数值、NaN/Inf。
- **方程版本三层次**：`equation_version` = 方程函数与显式依赖（如 clamp）的
  源码 sha256；`parameter_version` = 参数值 + 来源路径摘要；`resolved_version`
  = 方程 + 参数 + 边界情况的组合摘要；整个声明另有 `declaration.hash`。
  源码不可读（打包环境）时拒绝生成无来源版本。

## 3. C0/C1 构造期验收

注册表构造即执行全部 C0 校验与 C1 见证**实测重跑**，任何失败直接
`ValueError`——漂移无法在构造后存活：

- C0：节点/参数/外生源/机制的引用可解析、值域与参数值类型一致、
  微步已声明且同帧父必须位于更早微步、单写者、boundary 节点无写者、
  方程签名与声明绑定逐参数一致、无隐式默认。
- C1：每个父模板恰有一个版本绑定的见证，构造时用当前方程源码重跑，
  输出与冻结预期值逐位一致且两臂输出确实不同。

契约测试见 `backend/tests/unit/test_causal_registry.py`（重复声明、
签名漂移、见证陈旧、值域越界、参数类型不符等负例全覆盖）。

`derive.py` 的三个公共函数（`derive_latitude` / `derive_seasonal_amp` /

**边界**：统一天气场、`_compute_params` 其余节点、区域事件等**尚未登记**，
不作为已覆盖声明；新增机制按同一流程逐个进入（见 §6）。

## 5. 快照与防漂移管线

```text
生产注册表（backend/ascend/weather/mechanisms.py）
   │ export_registry.py           .venv/bin/python research/equations/export_registry.py
   ▼
research/equations/equations.json（schema v2，自动生成，禁止手改）
   │ gen_lean.py                  .venv/bin/python research/equations/gen_lean.py
   ▼
research/lean/.../GenDeclarationData.lean（数据段 + 对账定理）
```

- `export_registry.py --check`：入库 JSON 与注册表逐字节一致，否则非零退出；
- `gen_lean.py --check`：Lean 生成物与 JSON + config 真值一致；
- 两个门禁已接入 `.github/workflows/lean_action_ci.yml`，watch 路径覆盖
  `backend/ascend/causal/**`、`weather/derive.py`、`weather/mechanisms.py`、
  `space/climate.py`、`config.py`、`data/world.json`；
- 研究侧图投影（`schema.py` v2 加载 `variables/edges`）仅供
  `graph_check.py` / `gen_lean.py` 消费，不再反向驱动生产。

## 6. 新增机制的流程

1. 在机制所属模块定义纯方程函数（无隐式默认参数、无变参）；
2. 在注册表登记 `NodeSpec`（输出节点 origin=mechanism）、`ParentSpec`、
   所需 `ParameterSpec`/`ExogenousSourceSpec` 与至少每条父边一个
   `DependencyWitness`（冻结输入与预期输出）；
3. 生产调用点改为 `WEATHER_MECHANISMS.evaluate(...)`，删除就地公式；
4. 重跑 `export_registry.py` 与 `gen_lean.py`，提交生成的
   `equations.json` 与 `GenDeclarationData.lean`；
5. 两个 `--check` 门禁 + `verify_equations.py` + `graph_check.py` 全绿后合并。
