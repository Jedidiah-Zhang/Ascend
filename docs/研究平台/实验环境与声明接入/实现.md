## 2. 实现方案

### 引擎与入口

核心位于 `kheker/native/`，采用 C++17 标准库和 CMake，生成静态库 `ascend_engine`，调用方链接目标为 `ascend::engine`。当前同进程调用，不依赖 Qt、Godot、Python 或第三方运行库。后续 Qt [工作台](../因果建模工作台/实现.md)通过核心接口接入，界面与事件循环不进入核心。

当前流程为：构造 `Module` 并声明提供项／需求项与子模块 → 显式接线、转接需求及导出接口 → `Engine::add` 校验整棵子树并登记 → `check` 汇总引用与装配诊断 → `seal` 一次发布运行装配 → testbench 通过顶层公开入口驱动。目录在注册期间即可浏览；封闭成功后目录和连接固定。宿主及模块代码组织调用顺序，组合树不生成调度表。

当前工程位置承载研究接入切片；后续共享核心拆分、模型文件、跨语言绑定和原生插件 ABI 尚未定稿。未来世界基底可按接口接入；当前新世界库运行时尚未实现，本切片不依赖或加载重构前已移除的 Python 世界运行时。

### 声明与校验接入

`Module::add_value<T>` 绑定 getter，`add_method<R, Args...>` 绑定方法及其参数名称；原生类型由模板声明，运行时使用 `std::type_index` 精确匹配。`std::any` 负责值传递，支持可复制的模块自定义类型，包括由模块自行定义的矩阵结构；没有内置空间量或通用张量布局。

`Declaration` 暴露引用、符号种类、结果类型、参数名称与类型、契约标识、说明和声明读写引用。`Requirement` 描述所需的接口契约和签名，需求对象在回调中通过 `Context` 解析到当前实例的已连接入口。无依赖的回调仍可使用原来的普通 C++ 函数签名。

模块配置校验在登记子树前执行；方法内的领域检查由实现负责。诊断包含 `ErrorCode`、目标 `Reference` 和消息，嵌套实例以完整路径定位。`check` 返回全部装配错误，`seal` 失败抛出第一项并保持注册开放；可用 `Engine::add(..., scope)` 补齐模块，用 `disconnect`／`connect` 修正连接后重试。诊断按目标排序，嵌套调用错误的消息保留内层接口位置；没有部分发布的绑定。

语义说明不触发数学推理或正确性认证。目录查询不执行 getter；声明读写引用只检查目标存在且为公开量，不追踪函数内部访问、不自动生成调度计划。回调异常转换为相应诊断，异常前已经产生的模块状态改变不回滚。

类型化绑定通过 `detail::transport_value` 将参数封装和结果解包纳入异常转换，覆盖自定义类型复制／移动时抛出的标准及非标准异常；目标引用取自绑定入口。调用检查和回调已有的诊断保持原样。

### 数据访问与后续范围

值通过 getter 读取，返回 C++ 值副本；方法接收显式参数，可操作其回调捕获的数据。原生类型中的指针或共享资源仍由模块管理，值复制不等于深复制全部状态。重复使用同一个模块构建对象可能共享回调及其状态；独立运行应各自创建所需数据和模块。

类型化绑定句柄持有整个封闭运行时，脱离引擎对象后仍可调用相互连接的模块。`Context` 只持有运行时弱引用；保留下来的上下文在运行时销毁后返回明确诊断。需求声明不拥有提供方，允许有终止条件的相互调用且不产生内部所有权环。外部借用资源的生命周期由模块作者保证。

当前为单线程宿主接口，未提供并发或事务保证。上下文只解析本实例声明的需求，不约束 C++ 代码对外部对象的访问；只读视图、受管理批量写入及实际访问核验仍为后续候选，值传递成本尚未测量。

引擎可按声明提供过去值或窗口，机制记忆可通过状态输入与状态输出延续。具体保管、恢复及访问方式仍为候选，无需默认保存全部调用历史。

### 最小执行切片

已实现无空间、实体或游戏时钟依赖的两变量示例。宿主创建模块并调用两次 `advance`，公开量 `a`、`b` 由 getter 读出；执行方法附带声明读写引用。

示例计算为 `a_next = a`、`b_next = b + 2 * a`。从 `(2, 0)` 出发，两次调用后为 `(2, 8)`；另一独立实例从 `(3, 0)` 出发得到 `(3, 12)`。示例使用 `std::int64_t` 和固定小数值，验证条件变化与实例隔离；它不是快照分支或干预协议的实现，也不规定通用更新方式。

### 多模块装配与 testbench

`assembled_model.cpp` 中 `baseline`／`alternate` 各自包含 `model` 组合，组合内有 `state` 与 `update`。更新模块声明输入值、旧状态和写入方法三个需求；装配显式接线，顶层只导出 `advance` 和 `output`。testbench 创建初始状态为 `0` 的两套实例，分别通过可变输入模块驱动不同值；每轮先驱动输入、显式调用 `advance`、随后采样输出。

```text
testbench → drive inputs → baseline.advance  → sample baseline.output
                         → alternate.advance → sample alternate.output
```

工厂每次创建新的状态对象；作用域区分局部同名模块。组合的外部需求用 `forward` 逐层转接，对外入口用 `export_symbol` 逐层导出，实际调用直接进入提供方代码。类型化需求对象只携带声明，`Context` 提供当前实例的连接，不依赖全局唯一的服务实例。

输入由公开 `drive(value)` 方法更新，不直接修改受测模块的私有状态。示例三轮输入分别为 baseline `[2, 1, 1]`、alternate `[3, 2, 1]`；每轮调用两套系统的 `advance` 后读取输出：

```text
pulse=1 baseline=4 alternate=6
pulse=2 baseline=6 alternate=10
pulse=3 baseline=8 alternate=12
```

这里的 `pulse` 只是 testbench 的轮次标签；每次推进都是宿主显式调用，不代表引擎提供全局时钟、自动调度、跨输入原子性或时间语义。

`catalog(scope)`、`requirements(scope)` 和 `connections(scope)` 可按组合浏览直接子模块的接口、需求与接线；`candidates(requirement, scope)` 按种类、精确类型和契约标识筛选当前作用域的候选。检索不自动接线，候选存在不表示其依赖已经满足；未解析的导出通过检查诊断呈现，暂不出现在已解析接口目录中。运行入口仅接受顶层公开引用，目录浏览不授予直接调用内部接口的能力。

ctest --test-dir build/work/native --build-config Debug --output-on-failure

## 5. 验证与性能

按[设计验收](设计.md#7-验收标准)建立检查，记录规则编号、输入条件、执行入口及结果。接口检查、模块校验和实现测试分别记录覆盖范围；新研究保证须有对应证据，声明检查通过不能扩展为基底正确性证明。

测试覆盖非空间计算、自定义值传递、目录无副作用、模块作用域、重复与无效声明、配置校验及重入、缺失依赖、生命周期、类型与参数检查、异常以及句柄存活期。新增三个回归用例分别覆盖类型化参数复制、公开量结果移动、方法结果移动失败，均检查标准及非标准异常转换，以及方法是否已经执行；修复前这三个用例均因裸异常失败。

装配切片现有 15 项接口测试，覆盖嵌套需求转接与导出、作用域边界、候选检索、多个提供方的显式选择、缺失连接及修正、契约／签名不匹配、注册顺序、实例隔离、引用环的有限调用与资源释放、上下文失效、跨实例需求解析、子树校验、嵌套异常定位，以及外部输入驱动不隐式推进、显式调用后采样输出。另有 1 项可执行 testbench 输出检查；原有 21 项继续通过，共 37 项 CTest。

本次在 Linux x86-64 上验证：

| 构建 | 结果 |
| --- | --- |
| GCC 16.2.1，C++17，Debug | 37 项 CTest 全部通过，多模块示例第三次驱动输出 `pulse=3 baseline=8 alternate=12` |
| Clang 22.1.8，C++17，RelWithDebInfo，AddressSanitizer＋UndefinedBehaviorSanitizer | 相同 37 项全部通过，无 sanitizer 报告 |

Clang 检查使用 `-fsanitize=address,undefined -fno-omit-frame-pointer`。这些结果覆盖当前接口及测试用例，不构成任意模块的确定性或基底正确性证明。没有性能测量，不作吞吐承诺。

跨平台 CI 配置 Linux、Windows、macOS 构建并运行相同测试；配置本身不代表这些平台已验证通过。当前原生类型与标准库对象只用于同进程构建，不承诺跨工具链插件 ABI，也不保证任意浮点或第三方计算逐位一致。
