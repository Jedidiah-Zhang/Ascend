## 1. 设计依据

依据设计中的[目标与达成情况](设计.md#2-目标与达成情况)，当前实现覆盖 G-01、G-02，并在 G-03、G-04 的部分范围落地，遵循 [ENV-01～08](设计.md#4-已确认规则)。历史、随机、干预、模型声明文件与访问核验尚未实现。设计规则由设计文档维护，本文不重复。

## 2. 代码结构

### 工程布局

核心位于 `kheker/native/`，采用 C++17 与 CMake，构建为静态库 `ascend_engine`，调用方链接目标为 `ascend::engine`，不依赖 Qt、Godot、Python 或第三方运行库。公共接口为 [engine.hpp](../../../kheker/native/include/ascend/engine.hpp)、[assembly.hpp](../../../kheker/native/include/ascend/assembly.hpp)、[text.hpp](../../../kheker/native/include/ascend/text.hpp) 与 [i18n.hpp](../../../kheker/native/include/ascend/i18n.hpp)，分别对应引擎、装配、基础文本模型与语言目录。实现位于同名 `.cpp` 文件；内部 [json.cpp](../../../kheker/native/src/json.cpp) 与 `json.hpp` 提供 JSON 编解码。核心 `i18n/zh-CN.json` 维护 `ascend.engine` 文本域；示例文案分别位于 `examples/accumulator/i18n/` 与 `examples/stimulus/i18n/`。`examples/` 有四个可执行示例，测试位于 `testbench/native/`。

### 模块与引用

`Module` 保存模块名、公开项、需求项、子模块、连接与导出，并可携带配置校验函数。`add_value` 绑定只读公开量；`add_method` 声明参数名称、结果类型与读写依赖并绑定实现；`require_value` 与 `require_method` 声明需求并返回类型化需求对象，携带符号种类、精确 C++ 类型、参数与契约标识。`Reference` 由模块名与符号名组成，不依赖分隔符或领域内置概念。`Context` 只解析当前实例声明的需求，以弱引用保存，不延长运行装配的生命周期。

### 引擎的装配与调用

`Engine` 持有一个根作用域。装配阶段依次是添加模块与子模块、显式接线、`check` 汇总全部诊断、`seal` 发布运行装配。`seal` 成功后模块集合与连接固定；失败时抛出第一项诊断并保持注册开放，可以继续补齐模块，或用 `disconnect`／`connect` 修正连接后重试。运行阶段提供目录、需求、连接与兼容候选查询，以及 `read`／`call` 和类型化绑定 `bind_value`／`bind_method`；绑定句柄持有完整运行装配，名称解析在取得句柄时完成。诊断由错误类别、目标引用与结构化消息组成，可附带记录来源、字段路径与内层原始诊断；嵌套调用通过 `cause` 保留内层接口位置。

### 声明接入与类型传输

公开量与方法的声明由模板在编译期取得原生类型，运行时以 `std::type_index` 精确匹配，不做隐式数值转换；`std::any` 承载值传递，要求值类型可复制。参数封装与结果解包集中在 `detail::transport_value`，标准及非标准异常都转换为带目标引用的执行诊断。参数封装失败时方法尚未执行；结果解包失败时方法已经完成的状态变化继续保留。回调可以接收 `Context`，无依赖的回调仍可使用普通 C++ 函数签名。

### 工厂与装配定义

`ModuleFactoryDirectory` 把模块定义标识映射到构造入口。构造入口接收实例名与 `Config`，每次调用重新执行并返回新实例。工厂抛出的 `EngineError` 保留错误类别，外层 `target` 定位所属实例，`cause` 持有内部原始诊断；经记录实例化时，外层附加实例记录位置，内部来源不被覆盖。返回名称与实例名不一致、标准及非标准的其他异常按 `invalid_config` 报告。`Config` 承载空值、布尔、有符号整数、浮点、字符串、数组与对象；整数按 `std::int64_t` 精确解析并检查范围，字段、默认值与合法范围由工厂解释。

`AssemblyDefinition` 以作用域树保存实例（定义标识、实例名、构造配置）、连接、需求转接与接口导出；同一份定义驱动 `to_json`／`save` 与 `instantiate`，不在保存器和执行器分别维护连接关系。实例化先登记根实例，再递归构建并登记根下的子作用域，最后处理根连接，返回未封闭的 `Engine`；任一阶段失败时临时引擎及模块释放，不向调用方发布部分实例，已加载的实例不受影响。记录中的转接只指向直接子需求，`forward_inherited` 在需求尚未声明时继承其种类、签名与契约，转接失败撤销本次新增的需求，保留已有声明。

### 记录格式与加载

记录字段及失败语义由[装配记录契约](设计.md#装配记录)维护。`parse`／`load` 先完成语法、格式版本与结构检查；`instantiate` 再执行工厂查找、构造与装配。文件读取失败按 `io_failure` 报告，语法错误携带来源与行列，字段错误附加 JSON Pointer 路径。

JSON 编解码位于内部 `json.cpp`，只依赖标准库。解析与输出共用 UTF-8 校验和容器深度限制；`save` 先完成序列化再打开目标文件。引擎保存需求、接线与导出的来源映射，供后续 `check`／`seal` 使用；连接修改会清除旧接线位置。`Diagnostic::cause` 使用不可变诊断的共享所有权，`EngineError::what()` 逐层输出原因链。

### 通用文案层

行为契约见[模块文案与诊断展示](设计.md#模块文案与诊断展示)。[text.hpp](../../../kheker/native/include/ascend/text.hpp) 定义 `TextKey`、`TextRef` 和 `I18nResource`，不依赖引擎、装配或 JSON。`TextRef` 按值保存原文或带域的消息树，字段只读，通过构造器检查参数与深度；默认模板用 `std::optional` 区分缺失与空文本。声明、方法选项与需求的 `description` 统一使用 `TextRef`。

[text.cpp](../../../kheker/native/src/text.cpp) 的 `render_text` 对选中模板进行单次扫描，递归渲染匹配参数后直接插入结果，不重新扫描插入内容。[i18n.hpp](../../../kheker/native/include/ascend/i18n.hpp) 定义 `TextCatalog`，以语言和 `TextKey` 为索引；`define` 登记单条翻译，`load` 接收 `I18nResource`，`resolve` 只接收结构化文本。`TextConflict::reject` 为默认行为，`replace` 显式允许覆盖。语言文件加载位于 [i18n.cpp](../../../kheker/native/src/i18n.cpp)，复用 `Config` 与内部 JSON 解析，检查后在目录副本上合并并交换发布；其复制成本随已有目录规模增长，目前没有性能测量。

`Diagnostic::text` 是消息的唯一来源；`render_diagnostic` 渲染消息及完整原因链，`EngineError` 构造时缓存默认语言结果供 `what()` 使用。读取、调用、配置校验与值传输通过 `detail::rethrow_boundary` 统一转换异常，工厂与上述入口共用 `wrap_diagnostic` 保存内部诊断。提供方与转接不匹配的原因作为嵌套 `TextRef` 保存。展示层解析消息不会修改原诊断，也不把已渲染字符串再次当成模板。

`ModuleFactoryDirectory::add_definition` 可随工厂登记资源列表，`i18n_resources(definition)` 查询列表；两者都不加载文件或构造实例。宿主按需加载资源，多个实例共用定义级文本。`ascend_text_catalog` 示例演示资源登记、加载与两实例共享说明。核心语言包只维护引擎诊断，示例语言包独立维护；默认模板仍随模块代码提供。尚无安装器、自动资源发现、复数规则、日期数字格式化或翻译参数静态核验。

## 3. 当前实现范围与限制

已实现的范围包括：作用域内实例与符号唯一性，提供项与需求项的声明、逐项显式连接、需求转接与接口导出，兼容候选查询；类型化绑定与调用、实例上下文、契约标识与精确签名匹配；登记前的子树配置校验与嵌套位置诊断；封闭时一次发布运行装配、失败可修正、外部绑定句柄保活；模块工厂、装配定义、保存加载与独立实例；记录来源与字段路径诊断，以及加载失败不发布部分实例；结构化文本与诊断树、模块文本域与资源登记、语言回退、单次占位符替换及显式冲突处理。

尚未实施：模型声明文件加载、自动调度、历史与快照、随机管理器、干预协议、实际访问追踪、插件装载以及 Qt 界面。装配记录只覆盖装配定义与构造配置，不保存模块私有状态或运行状态。

边界与限制：当前为单线程宿主接口，不提供并发或事务保证；原生类型只用于同进程匹配，不承诺跨工具链插件 ABI；公开量读取返回值副本，值复制不等于深复制全部状态；模块回调及外部借用资源的生命周期由模块作者负责；上下文只解析本实例声明的需求，不约束模块代码以其他方式访问外部对象；引擎核心不持有语言状态，诊断的默认语言消息在抛出时渲染，展示层按语言文件另行解析；没有性能测量，不作吞吐承诺。

## 4. 构建与运行入口

依赖 CMake 3.20 及支持 C++17 的编译器。在仓库根目录执行：

```bash
cmake -S kheker/native -B build/work/native -DCMAKE_BUILD_TYPE=Debug -DBUILD_TESTING=ON
cmake --build build/work/native --config Debug --parallel 4
ctest --test-dir build/work/native --build-config Debug --output-on-failure
```

构建产物位于已忽略的 `build/work/native/`。单配置构建的示例入口为 `build/work/native/ascend_minimal_model`，输出 `baseline=8 alternate=12`；`ascend_assembled_model` 驱动两套组合并逐轮输出采样结果；`ascend_assembly_record` 先构建装配定义，写入系统临时目录下随机创建的 `ascend-assembly-record-…/record.json` 后再加载、封闭并由同一测试程序驱动，运行结束后清理临时目录。文案示例在仓库根目录运行 `build/work/native/ascend_text_catalog kheker/native/i18n/zh-CN.json kheker/native/examples/accumulator/i18n/zh-CN.json`，输出 `catalog=ok`。Visual Studio 等多配置生成器在 `build/work/native/<配置>/` 下生成对应可执行文件。测试程序、用例清单与验证环境见[测试文档](测试.md)。
