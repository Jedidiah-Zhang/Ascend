## 2. 实现方案

### 引擎与入口

引擎负责模型加载、目录与依赖查询、检查、机制调用及诊断。[工作台](../因果建模工作台/实现.md)和无界面入口复用这些能力。模型文件、机制代码与工具视图分离，具体存储格式、语言、进程与绑定方式未定。

候选执行流程为：解析定义与引用 → 对应变量和函数输入输出 → 检查所支持的条件 → 形成执行描述 → 运行并返回结果与诊断。具体中间表示、编译与解释的分工尚未选择，不预设必须生成原生代码。

运行基底通过其声明与实现接入，不要求内部全部由模型声明语言编写。研究者自定义基底的可用性由其维护，声明检查只报告实际覆盖的条件。

### 数据访问候选

机制函数可通过显式参数或受限上下文访问模型数据、已声明全局量及随机入口。两种方式的依赖核验、调用成本和可扩展性需比较；不承诺自动识别任意函数的全部外部访问。

历史可按声明提供过去值或窗口，机制记忆可通过旧状态输入、新状态输出延续。具体保管、恢复及访问方式仍为候选，无需默认保存全部调用历史。

旧随机实现 `olam/kernel/rng.py` 及[归档随机设计](../../归档/世界框架/随机系统/设计.md)可供比较：以种子和结构化地址派生随机值，减少消费顺序对配对的影响。旧算法、地址字段与帧号约定均未获采用。

### 最小执行切片

先以少量变量和机制函数检验声明、绑定、检查与无界面执行，再提供工作台查询和诊断接口。试运行与条件对比在对应执行及干预语义明确后接入。

**候选验证用例**：确定性两变量系统 `a_next = a`、`b_next = b + 2 * a`，右侧均读取更新前的值。从 `(2, 0)` 出发，两次更新后为 `(2, 8)`；首次更新前将 `a` 设为 `3` 的分支，两次更新后为 `(3, 12)`。这些数值和更新方式仅供手算核对，不是通用平台规则。错误引用、绑定及不受支持的访问用例随接口定义补齐。
