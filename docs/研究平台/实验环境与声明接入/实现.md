## 1. 设计依据

依据设计中的[目标与达成情况](设计.md#2-目标与达成情况)，当前实现覆盖 G-01、G-02，并在 G-03、G-04、G-06、G-08 的部分范围落地，遵循 [ENV-01～13](设计.md#4-已确认规则)。模型声明文件、随机、历史、行动通道与访问核验尚未实现；状态交接与实验记录仅进程内。设计规则由设计文档维护，本文不重复。

## 2. 代码结构

### 工程布局

核心位于 `kheker/engine/`，采用 C++17 与 CMake，构建为静态库 `ascend_engine`，调用方链接目标为 `ascend::engine`，不依赖 Qt、Godot、Python 或第三方运行库。公共接口为 [engine.hpp](../../../kheker/engine/include/ascend/engine.hpp)（引擎、模块与状态交接）、[config.hpp](../../../kheker/engine/include/ascend/config.hpp)（结构化配置值）、[state.hpp](../../../kheker/engine/include/ascend/state.hpp)（运行状态快照）、[assembly.hpp](../../../kheker/engine/include/ascend/assembly.hpp)（装配定义与模块工厂）、[experiment.hpp](../../../kheker/engine/include/ascend/experiment.hpp)（实验运行、干预与轨迹记录）、[text.hpp](../../../kheker/engine/include/ascend/text.hpp) 与 [i18n.hpp](../../../kheker/engine/include/ascend/i18n.hpp)（文本模型与语言目录）。实现位于同名 `.cpp` 文件；内部 [json.cpp](../../../kheker/engine/src/json.cpp) 与 `json.hpp` 提供 JSON 编解码，`engine_internal.hpp` 保存 `Entry`、`Runtime`、`StateEntry` 等实现类型与失败辅助。公共头只保留契约、擦除句柄与模板入口，不暴露内部类型。核心 `i18n/zh-CN.json` 维护 `ascend.engine` 文本域；示例文案分别位于 `examples/accumulator/i18n/` 与 `examples/stimulus/i18n/`。`examples/` 有五个可执行示例，测试位于 `testbench/engine/`。

### 模块与引用

`Module` 保存模块名、公开项、需求项、子模块、连接与导出，并可携带配置校验函数。`add_value` 绑定只读公开量；`add_method` 声明参数名称、结果类型与读写依赖并绑定实现；`require_value` 与 `require_method` 声明需求并返回类型化需求对象，携带符号种类、精确 C++ 类型、参数与契约标识。`Reference` 由模块名与符号名组成，不依赖分隔符或领域内置概念。`Context` 只解析当前实例声明的需求，以弱引用保存，不延长运行装配的生命周期。

### 引擎的装配与调用

`Engine` 持有一个根作用域。装配阶段依次是添加模块与子模块、显式接线、`check` 汇总全部诊断、`seal` 发布运行装配。`seal` 成功后模块集合与连接固定；失败时抛出第一项诊断并保持注册开放，可以继续补齐模块，或用 `disconnect`／`connect` 修正连接后重试。未封闭时的目录查询复用一份草稿，模块或连接变化后失效重建。运行阶段提供目录、需求、连接与兼容候选查询，以及 `read`／`call` 和类型化绑定 `bind_value`／`bind_method`；绑定句柄持有完整运行装配，名称解析在取得句柄时完成。诊断由错误类别、目标引用与结构化消息组成，可附带记录来源、字段路径与内层原始诊断；嵌套调用通过 `cause` 保留内层接口位置。

### 声明接入与类型传输

公开量与方法的声明由模板在编译期取得原生类型，运行时以 `std::type_index` 精确匹配，不做隐式数值转换；`std::any` 承载值传递，要求值类型可复制。参数封装与结果解包在绑定模板中进行，异常经不透明的绑定句柄统一转换为带目标引用的执行诊断。参数封装失败时方法尚未执行；结果解包失败时方法已经完成的状态变化继续保留。回调可以接收 `Context`，无依赖的回调仍可使用普通 C++ 函数签名。

### 工厂与装配定义

`ModuleFactoryDirectory` 把模块定义标识映射到构造入口。构造入口接收实例名与 `Config`，每次调用重新执行并返回新实例。工厂抛出的 `EngineError` 保留错误类别，外层 `target` 定位所属实例，`cause` 持有内部原始诊断；经记录实例化时，外层附加实例记录位置，内部来源不被覆盖。返回名称与实例名不一致、标准及非标准的其他异常按 `invalid_config` 报告。`Config` 承载空值、布尔、有符号整数、浮点、字符串、数组与对象；整数按 `std::int64_t` 精确解析并检查范围，字段、默认值与合法范围由工厂解释。

`AssemblyDefinition` 以作用域树保存实例（定义标识、实例名、构造配置）、连接、需求转接与接口导出；同一份定义驱动 `to_json`／`save` 与 `instantiate`，不在保存器和执行器分别维护连接关系。实例化先登记根实例，再递归构建并登记根下的子作用域，最后处理根连接，返回未封闭的 `Engine`；任一阶段失败时临时引擎及模块释放，不向调用方发布部分实例，已加载的实例不受影响。生成的纯作用域容器显式声明无状态，子模块仍各自接受完整状态检查。记录中的转接只指向直接子需求，`forward_inherited` 在需求尚未声明时继承其种类、签名与契约，转接失败撤销本次新增的需求，保留已有声明。

### 记录格式与加载

记录字段及失败语义由[装配记录契约](设计.md#装配记录)维护。`parse`／`load` 先完成语法、格式版本与结构检查；`instantiate` 再执行工厂查找、构造与装配。文件读取失败按 `io_failure` 报告，语法错误携带来源与行列，字段错误附加 JSON Pointer 路径。

JSON 编解码位于内部 `json.cpp`，只依赖标准库。解析与输出共用 UTF-8 校验和容器深度限制；`save` 先完成序列化再打开目标文件。引擎保存需求、接线与导出的来源映射，供后续 `check`／`seal` 使用；连接修改会清除旧接线位置。`Diagnostic::cause` 使用不可变诊断的共享所有权，`EngineError::what()` 逐层输出原因链。

### 通用文案层

行为契约见[模块文案与诊断展示](设计.md#模块文案与诊断展示)。[text.hpp](../../../kheker/engine/include/ascend/text.hpp) 定义 `TextKey`、`TextRef` 和 `I18nResource`，不依赖引擎、装配或 JSON。`TextRef` 按值保存原文或带域的消息树，字段只读，通过构造器检查参数与深度；默认模板用 `std::optional` 区分缺失与空文本。声明、方法选项与需求的 `description` 统一使用 `TextRef`。

[text.cpp](../../../kheker/engine/src/text.cpp) 的 `render_text` 对选中模板进行单次扫描，递归渲染匹配参数后直接插入结果，不重新扫描插入内容。[i18n.hpp](../../../kheker/engine/include/ascend/i18n.hpp) 定义 `TextCatalog`，以语言和 `TextKey` 为索引；`define` 登记单条翻译，`load` 接收 `I18nResource`，`resolve` 只接收结构化文本。`TextConflict::reject` 为默认行为，`replace` 显式允许覆盖。语言文件加载位于 [i18n.cpp](../../../kheker/engine/src/i18n.cpp)，复用 `Config` 与内部 JSON 解析，检查后在目录副本上合并并交换发布；其复制成本随已有目录规模增长，目前没有性能测量。

`Diagnostic::text` 是消息的唯一来源；`render_diagnostic` 渲染消息及完整原因链，`EngineError` 构造时缓存默认语言结果供 `what()` 使用。读取、调用、配置校验与值传输通过内部失败边界统一转换异常，工厂与上述入口共用 `wrap_diagnostic` 保存内部诊断。提供方与转接不匹配的原因作为嵌套 `TextRef` 保存。展示层解析消息不会修改原诊断，也不把已渲染字符串再次当成模板。

`ModuleFactoryDirectory::add_definition` 可随工厂登记资源列表，`i18n_resources(definition)` 查询列表；两者都不加载文件或构造实例。宿主按需加载资源，多个实例共用定义级文本。`ascend_text_catalog` 示例演示资源登记、加载与两实例共享说明。核心语言包只维护引擎诊断，示例语言包独立维护；默认模板仍随模块代码提供。尚无安装器、自动资源发现、复数规则、日期数字格式化或翻译参数静态核验。

### 模块状态交接

状态契约与规则见[ENV-09、ENV-10](设计.md#env-09-模块运行状态声明与完整捕获)。声明入口有两条：`Module::add_state` 接收状态契约与捕获／恢复回调，把模块声明为有状态；`declare_stateless` 把模块声明为明确无状态。两者互斥，重复声明与非法契约都被拒绝。状态值使用 [config.hpp](../../../kheker/engine/include/ascend/config.hpp) 的 `Config` 结构化数据；回调以 `std::function<Config()>`／`std::function<void(const Config&)>` 类型擦除保存。声明保存在 `Module::StateDeclaration`，运行期映射保存在内部 `detail::StateEntry`；`AssemblyBuilder` 为每个非根模块登记一个条目，未声明的模块保留未声明标记。

`Engine::capture_state` 返回按模块路径排序的 `StateSnapshot`：有状态模块调用其捕获回调取得状态值，无状态模块记空值；任一模块未声明状态能力时报 `state_incomplete`，运行保持不变；捕获回调抛出的异常按 `invalid_state` 包装。

`Engine::restore_state` 分三步：先按路径核对目标实例与快照的模块集合（与条目顺序无关）、状态契约与无状态标记，不匹配报 `state_mismatch`；再拒绝无状态条目携带的非空状态值；最后逐模块调用恢复回调写回。回调失败按 `invalid_state` 包装并保留作者诊断；中途失败不回滚已恢复的模块。

捕获与恢复经 `FailureBoundary::state_capture`／`state_restore` 统一转换异常。快照按值保存，要求捕获回调返回独立副本。状态声明不进入装配记录，也不改变 `seal` 生命周期。

### 实验运行与干预记录

实验契约与失败语义见[运行状态与实验切片](设计.md#运行状态与实验切片)。[experiment.hpp](../../../kheker/engine/include/ascend/experiment.hpp) 定义实验切片的公开类型：`ExperimentSpec`（推进入口、命名输入与命名观测）、`Observation`（边界与主体观测）、`Sample`（边界、完整真值与观测）、`Checkpoint`（边界与真值）、`Intervention`、`apply_interventions`、`StepFailure`、`RunTrace`、`DrivenInput`、`ExperimentRecord` 与 `ExperimentRun`。

`ExperimentRun` 构造时以装配定义与工厂目录完成实例化、检查与封闭，并绑定无参数推进入口；规格名称的校验先于实例化执行。`drive` 经引擎的调用检查驱动命名输入；`step` 在模型执行前检查边界上限，成功后使边界前进；`observe` 只读取规格声明的公开量，不调用状态捕获；`sample` 先捕获完整真值，再读取相同观测；`checkpoint` 捕获当前边界与真值组成检查点；`restore` 先校验检查点边界非负，再按检查点恢复，失败时边界不变。六类操作均使用内部 `Operation` 栈守卫拒绝同一运行的回调重入，正常与异常退出均释放保护；诊断目标含分支标签与被拒绝的操作名。

`apply_interventions` 在检查点副本上修改模块状态，按状态对象内的字段路径定位：字段路径以 `/` 分隔对象成员，空字段路径表示整个状态对象，首版不支持数组下标。目标模块缺失、目标无状态、路径经过非对象或字段不存在时报 `invalid_intervention`，原检查点不受影响；同一路径的多次修改按请求顺序应用。

`RunTrace` 由调用方填充分支标签、共同起点、干预、逐步采样与 `StepFailure`（停留边界与诊断）。`ExperimentRecord` 把装配定义、实验规格、定义到实现标识的映射、`DrivenInput` 共同输入列表和各分支轨迹保存为一个进程内值对象。宿主负责记录与实际调用一致并核对工厂实现身份。示例按该记录重建装配、恢复分支并逐边界核对真值和观测；测试还在原装配、工厂目录和运行销毁后使用变化的输入序列重放。

## 3. 当前实现范围与限制

已实现的范围包括：作用域内实例与符号唯一性，提供项与需求项的声明、逐项显式连接、需求转接与接口导出，兼容候选查询；类型化绑定与调用、实例上下文、契约标识与精确签名匹配；登记前的子树配置校验与嵌套位置诊断；封闭时一次发布运行装配、失败可修正、外部绑定句柄保活；模块工厂、装配定义、保存加载与独立实例；记录来源与字段路径诊断，以及加载失败不发布部分实例；结构化文本与诊断树、模块文本域与资源登记、语言回退、单次占位符替换及显式冲突处理；模块运行状态声明与完整捕获、按快照恢复与不匹配诊断、检查点分支、一次性外部状态干预、真值与观测采样及进程内轨迹记录。

尚未实施：模型声明文件加载、自动调度、历史与状态快照的文件编码、随机管理器、行动通道干预、实际访问追踪、插件装载以及 Qt 界面。装配记录只覆盖装配定义与构造配置，不保存模块私有状态或运行状态；本切片的状态快照只在进程内交接，不写入装配记录。

边界与限制：当前为单线程宿主接口，不提供并发或事务保证；原生类型只用于同进程匹配，不承诺跨工具链插件 ABI；公开量读取返回值副本，值复制不等于深复制全部状态；模块回调及外部借用资源的生命周期由模块作者负责；上下文只解析本实例声明的需求，不约束模块代码以其他方式访问外部对象；引擎核心不持有语言状态，诊断的默认语言消息在抛出时渲染，展示层按语言文件另行解析。状态方面：载体为结构化数据，不支持数组下标寻址、大张量或二进制载体；状态契约相等不证明结构兼容；恢复不核对实例配置差异；快照与轨迹记录不定义文件格式。

首版成本基线：研究采样先完整捕获真值，再读取观测；`observe` 只读取观测；轨迹按边界保存整份真值；干预复制整份快照，并沿字段路径复制途经的同级成员。因此记录内存随“步数 × 状态大小”增长。类型尺寸在本机构建（GCC 16.2.1 与 Clang 22.1.8、x86-64 Linux）以 `sizeof` 实测：Config 104 字节、ModuleState 176 字节、Sample 80 字节、RunTrace 136 字节；每个标量状态值都按完整 Config 计费。接入工作台、空间场或大张量之前，需要据此评估按需真值记录、干预定向修改与更紧凑的状态表示。没有性能测量，不作吞吐承诺。

## 4. 构建与运行入口

依赖 CMake 3.20 及支持 C++17 的编译器。在仓库根目录执行：

```bash
cmake -S kheker/engine -B build/engine -DCMAKE_BUILD_TYPE=Debug -DBUILD_TESTING=ON
cmake --build build/engine --config Debug --parallel 4
ctest --test-dir build/engine --build-config Debug --output-on-failure
```

构建产物位于已忽略的 `build/engine/`。单配置构建的示例入口为 `build/engine/ascend_minimal_model`，输出 `baseline=8 alternate=12`；`ascend_assembled_model` 驱动两套组合并逐轮输出采样结果；`ascend_assembly_record` 先构建装配定义，写入系统临时目录下随机创建的 `ascend-assembly-record-…/record.json` 后再加载、封闭并由同一测试程序驱动，运行结束后清理临时目录；`ascend_experiment_branch` 先在边界 2 建立共同检查点，再恢复出对照与干预分支（`x := 10`），同步驱动后续输入，逐边界打印两组结果并与参考核对，再依据实验记录重放。主体函数只接收 `Observation`。输出包含 `origin boundary=2 control=(2,1,0) treated=(10,1,0)`、`boundary=5 control=(5,4,6) treated=(13,12,22)`、`replay=ok` 与 `reference=ok`。文案示例在仓库根目录运行 `build/engine/ascend_text_catalog kheker/engine/i18n/zh-CN.json kheker/engine/examples/accumulator/i18n/zh-CN.json`，输出 `catalog=ok`。Visual Studio 等多配置生成器在 `build/engine/<配置>/` 下生成对应可执行文件。测试程序、用例清单与验证环境见[测试文档](测试.md)。
