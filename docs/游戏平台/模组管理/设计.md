# 模组管理 — 设计

> - 设计状态：讨论中
> - 适用范围：游戏模组选择、装配与变更后的存档续玩
> - 上级：[游戏平台](../综述.md) · [实现](实现.md)

## 1. 目标与意义

游戏要让玩家通过模组管理器组合官方与社区内容，并在配置变化后尽可能继续已有游戏。模组让规则与内容可以替换和扩展，但玩家的存档与进度不应该因为一次更新就被判废；这里需要在“数据仍能被解释”与“规则已经变化”之间给出清楚的判断。

本模块负责产品配置、跨部分连接、诊断及加载策略；世界模块的注册与执行接入见[声明与装配](../../世界/运行支撑/声明与装配/设计.md)。模组文件的安装、客户端资源和玩法配置不由世界库管理；包解析是否作为两平台共享工具、其代码归属及安装方式仍待确定。

## 2. 目标与验收

以下目标已确认，接口与候选策略见后文，落地范围见[实现](实现.md)。

| 目标 | 验收条件 | 规则 |
| --- | --- | --- |
| 默认官方游戏 | 安装并使用默认配置即可获得完整基础游戏，不需玩家自行寻找规则 | [MOD-01](#mod-01-官方基础游戏以模组装配) |

## 3. 概念与术语

模块、模组包、配置档与模组管理器的区别统一见[整体架构](../../整体架构.md#4-模块与装配边界)。包版本表示发布身份，存档结构版本表示数据解释方式；分别记录二者是候选方案，版本不同不直接等于数据不兼容。

## 4. 已确认规则

### MOD-01 官方基础游戏以模组装配

游戏在[必备基础框架](../../整体架构.md#4-模块与装配边界)之上通过模组管理器装配；基础游戏的机制与内容作为官方模组管理，可以由多个官方模组共同组成。模组管理器是游戏平台的一项能力，不是游戏平台的全部。

产品默认交付由官方模组组成的完整基础游戏，玩家无需自己寻找规则来组成游戏。模组化也不代表每个官方模块都可任意禁用。基础游戏所需模组、具体拆包、必需依赖和可选部分尚未确定。

框架与规则分离服务于扩展，不以仅有引擎作为独立游戏产品目标；研究者整体替换环境的边界由[研究平台](../../研究平台/综述.md#自定义因果实验环境)维护。

### MOD-02 社区算法不承担研究准入义务

社区模组可以提供新的可执行算法，不要求作者满足研究侧的完整因果声明、验证或精确复现规定。算法仍需通过工程接口正确接入；构建与安装分工见 MOD-04，可执行语言和产物格式尚未选择。

### MOD-03 配置变化不直接阻止续玩

游戏存档以持续游玩为目标，不因模组版本、配置或摘要发生变化就一概拒绝加载。应判断当前模块能否解释并恢复所需数据，而不是要求安装内容逐字节相同。规则变化后的未来可以按新规则演化，不要求重现更新前规则的后续轨迹。

不承诺任何模组删除都能无损恢复；真正无法解释的必要数据或依赖须具体处理。运行中替换代码与重新装配后加载先前保存的数据是不同能力。

### MOD-04 作者构建与使用者免编译

可执行模组由作者编译、构建并交付可安装产物；使用者安装后通过模组界面选择启用或禁用，无需编译模组或重编游戏。纯数据与资源不因此要求进行代码编译。依赖及接口兼容性仍需校验，启用成功不自动取得研究资格。

具体产物格式、支持平台、接口兼容范围和构建工具尚未选择。启用与禁用操作何时对会话生效另行定义，不据此承诺运行中代码热替换。

## 5. 对外契约

以下为**候选接口分解**，尚未形成实施规格。

配置解析接收选定的包与功能，输出已解析的装配清单及诊断；依赖、版本范围、可选部分、定义覆盖与冲突待确定。

跨部分装配把包的世界、智能体及平台部分分派给各自注册结果；必需入口、连接校验和失败清理待确定。

存档评估根据保存的配置与数据、新的装配集合，给出可用恢复路径；数据结构兼容性与无法恢复的必要依赖待确定。

新模块初始化接收已有游戏状态，为新模块建立所需状态；不假定已有地图已经按新生成规则演化。

迁移与恢复接收已保存数据及标识，给出当前可用的数据或缺失项；迁移次序、引用修复、失败处理及未识别数据的保留待确定。

## 6. 边界与失败行为

以下是兼容恢复的**候选策略**，具体采用方式需讨论：

| 场景 | 候选处理 |
| --- | --- |
| 代码或平衡参数更新，数据仍可解释 | 恢复状态并按新规则继续运行 |
| 新增模组或字段 | 使用已有存档初始化入口、默认值或迁移逻辑 |
| 数据结构变化或定义重命名 | 由模块提供迁移，使用稳定命名空间标识及重命名映射 |
| 移除模组或定义缺失 | 占位、替代、停用相应功能或保留未识别数据，避免静默删除可恢复内容 |
| 使用紧凑运行时编号 | 保存对应稳定标识映射，恢复时验证与重建 |
| 仅改变字体或翻译 | 不以资源摘要变化拒绝世界存档；若影响观测或输入映射，另行识别影响 |

配置档的格式、默认值和运行中可修改项均未定。建议存档记录保存时的模组集合及配置，用于诊断与恢复，不作为不可变化的身份锁。

## 7. 取舍与候选方案

建议官方内容与社区使用相同的公开扩展接口，降低特权入口导致的扩展障碍；此原则尚待确认。官方多包可以有依赖，不要求每包独立可玩。

候选装配流程为：选择配置，解析依赖及显式组合规则，分派各部分，校验接口与连接，创建会话或选择兼容恢复路径。解析结果不应由文件枚举的偶然顺序决定，覆盖与补丁组合需有明确规则。

建议首版在一次运行期间固定代码模块集合；这不限制已加载模组在运行中执行算法、创建实体或修改状态，也不阻止退出后调整配置再读档。代码热替换、表现资源热重载与存档迁移分别决策。

包依赖顺序不等于机制求值顺序，也不等于同刻输入裁决。新算法执行后端的比较见[声明与装配设计](../../世界/运行支撑/声明与装配/设计.md#7-取舍与候选方案)。

## 8. 待决问题

官方拆包、基础游戏必需模组与公共接口尚未确定，阻塞默认游戏装配定稿；必备框架的存在已确定，解决位置为架构及各内容模块。

包格式、依赖、覆盖与功能选择尚未确定，阻塞解析器和管理器，解决位置为本模块与平台公共工具边界。

新算法的语言、构建产物与兼容接口尚未确定，阻塞社区算法入口实施；作者构建、使用者免编译已确定，解决位置为声明与装配及对应平台接口。

初始化、迁移、缺失引用恢复尚未确定，阻塞兼容加载实现，解决位置为本模块、状态与公共保存能力。

运行中代码或资源热替换尚未确定，只阻塞对应热替换能力，在首版能力范围确认时解决。
