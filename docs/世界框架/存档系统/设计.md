# 存档系统 — 设计

存档系统回答三个问题：**存在哪、存什么、什么时候存**。

核心设计取向（Issue #13 讨论确认）：

- **实时存档**：世界状态持续落盘，玩家不需要"时刻记着存档"。崩溃/退出后恢复的就是最新状态，最多丢失数秒。
- **模型 A：一个存档位 = 一个世界**：存档位内含唯一的实时状态 + 若干手动快照（回退点）。手动保存 = 给当前世界添加一个回退点，不产生新世界。
- **手动快照 = 回退检查点**：玩家可随时创建，用于"从某个点重新继续游戏"。回滚前自动为当前状态创建快照（保护最新分支不丢失）。
- **加密目的 = 防其他工具篡改/直读**（非防读取/防迁移）：自动生成密钥随档分发，游戏自动解锁，存档可移植可分享；但其他工具拿到的是乱码，无法直接修改。

## 目录结构

```
~/.ascend/saves/                          # 存档根目录（可在设置中调整）
  <world_id>/                             # 一个存档位 = 一个目录 = 一个世界
    manifest.json                         # 明文元信息 + 密钥混淆串 secrets_blob
    state.json.enc                        # 时钟/玩家/天气状态（加密 + HMAC 签名）
    entities.json.enc                     # 实体表（Issue #25 后启用，加密 + 签名）
    chunks.db                             # chunk tile 数据（SQLite WAL，明文）
    events.db                             # 世界树归档（SQLite WAL，明文）
    continent.bin                         # 大陆宏观场缓存（可再生，随档分发秒开）
    snapshots/                            # 该世界的回退点集合
      @<时间戳>-manual.ascendsave         # 手动快照：zip 打包 → 整体加密
      @<时间戳>-auto.ascendsave           # 自动快照（回滚保护）
```

`<world_id>` 为 UUID hex。快照是**世界目录内的兄弟子目录**（与活文件同根，而非活文件的子目录）：回滚 = 用快照内容替换活文件，快照子目录在替换期间先移出再放回——快照自身不受影响（否则回滚会删除自己的回退点）。快照命名 `@<YYYY-MM-DD-HHMMSS>-<uniq>-<suffix>.ascendsave`，suffix 标识来源（`manual` 手动、`auto` 回滚保护），uniq 防止同秒覆盖。

## 文件格式

### manifest.json（明文）

```json
{
  "format_version": 1,
  "name": "我的世界",
  "seed": 123456789,
  "created_at": 1722729600,
  "last_played_at": 1722733200,
  "play_duration_sec": 3600,
  "game_time": 1728000,
  "world_id": "a1b2c3..."
}
```

- `game_time` 为最近一次写入的时钟 tick（存档选择页显示游戏内时间）。
- 明文原因：存档选择页（Issue #14）必须在免密钥下展示列表信息。

### key 信息（藏于 manifest.json 的 secrets_blob，随档分发）

- 密钥**不落盘为明文文件**：用 world_id + seed 派生密钥加密后藏进
  `manifest.json` 的 `secrets_blob` 字段（混淆层）。
- 语义：防的是"其他工具打开直读/篡改"（普通工具看到的是乱码），
  不防"懂行的人"——world_id/seed 在 manifest 明文，派生密钥可被推算。
  可移植、可分享，换机器可玩。
- **seed 创建时定案**（0/缺省即随机并写入 manifest）：blob 派生身份与
  manifest 出生即一致；旧版"首次进入才随机化"会导致 blob 身份失配、
  state 加解密失败（旧档经 `SaveManager.rekey` 迁移）。
- 真实防篡改防线：`state.json.enc` 的 HMAC 签名 + 读档时 SQLite
  `PRAGMA integrity_check`（结构性损坏检测）。

### state.json.enc

Fernet 加密的 JSON（格式见序列化），附 HMAC 签名。内容：

```json
{
  "clock": {"time": 1728000, "speed": 1.0, "paused": false},
  "player": {"entity_id": null, "x": 612.4, "y": 1000.8},
  "weather": {"seed": 123456789},
  "archive_max_timestamp": 1728000
}
```

- `player.entity_id`：玩家实体 ID（本期玩家位置随 state 保存；实体表全量持久化在 Issue #25 启用后改从 `entities.json.enc` 恢复）。
- `archive_max_timestamp`：本次写入时事件归档内最新事件时间戳，读档时钟对齐用。

### chunks.db / events.db

明文 SQLite（WAL 模式）。SQLite 增量实时写，无法整文件加密，且 tile/事件数据敏感度低。篡改防护：**读档时 `PRAGMA integrity_check` 校验**（结构性损坏拒绝加载；记录内字节翻转无页校验和，不在检测范围，属文档化限制）。

chunks.db 行 = **已加载 chunk 全量**（含确定性生成的 clean chunk）：
首次加载的 chunk 在保存脉搏时落盘，读档/重访直接恢复、免重新生成
（~1s/chunk）；已落盘坐标由内存单调集合记录（启动时从库重建），
重访内容不变不重写。BLOB 经 zlib 压缩存储（旧版明文格式读取兼容），
每个 chunk 约 104KB。玩家改动（dirty）必落盘，玩家修改不可再生。

### .ascendsave 快照单文件

zip 打包（含 manifest.json、state.json.enc、entities.json.enc、chunks.db、events.db 的文件字节）→ Fernet 整体加密 → HMAC 签名附加。读档时：校验签名 → 解密 → 展开为新的 `<world_id>/` 活目录（或覆盖回滚目标）。快照头部携带会话密钥（自包含解锁）：会话密钥每快照随机，只解锁该快照的 zip，不解锁世界。

## 实时写入（统一保存脉搏）

三样数据以**统一保存脉搏**（`SAVE_PULSE_INTERVAL`，默认 5s）同一点落盘：
`state.json.enc` + 事件 flush（events.db）+ chunk flush（chunks.db）。
崩溃 → 恢复到最近完成的脉搏，丢失统一 = ≤5s 尾部（"丢了最近 5s"而非
"丢了某类数据"；未落盘的 clean chunk 为确定性数据，丢失可重新生成）。
脉搏之间 LRU 淘汰写回仍然立即落盘（安全网）。

| 内容 | 时机 | 机制 |
|---|---|---|
| 事件 → events.db | 每个脉搏 | WorldTree.archive_pending()（flush-and-drop，见事件系统/技术.md） |
| chunk → chunks.db | 每个脉搏 + evict 即时 | ChunkStore.flush()（已加载全量落盘：dirty 或首次加载，已落盘跳过）+ LRU 淘汰写回兜底 |
| state.json | 每个脉搏 | 原子写（临时文件 + rename），加密 |
| entities.json | Issue #25 启用后 | 随脉搏 |
| 正常退出 | 排空保存队列做最终脉搏 | 同步 |

**异步保存线程**：tick 循环只做"到点入队"（`_maybe_save_pulse`，零 I/O 阻塞），
专用保存线程串行执行脉搏，固定顺序 **事件 flush → state 写入 → chunk flush**
（事件先于 state，保证 state 的 `archive_max_timestamp` 新鲜）；单槽位防堆积
（已有脉搏在途则跳过本次，脉搏天然可合并）。退出/快照时强同步排空。

- 崩溃恢复：最多丢一个脉搏间隔（默认 5s）的 state/事件/chunk（chunk 中
  未落盘的 clean 为确定性数据，丢失可重新生成）；SQLite 已提交
  数据由 WAL 保障，state 由 fsync 原子写保障。
- 实时写入期间不发布任何事件（存档是世界外元操作，不产生历史、不进因果图）。

## 读档流程（进程模型，不产生历史）

一进程一模式：菜单进程（服务模式，仅存档管理）与世界进程
（`run_server --world-id <id> [--snapshot <file>]`）分离。进入世界 /
回滚 = 前端停旧进程（SIGTERM 优雅退出落盘）、以目标参数拉起新进程；
前端经握手 + `world_initialized` 事件感知就绪（网络层先行：端口与
token 立即就绪，大陆生成期间可连收 world_progress）。

1. 回滚时先自动快照当前活目录分支（DB 未打开，直接打包，见 create_snapshot）。
2. 快照展开为活目录（extract_snapshot，目标 world_id 覆盖由 CLI 传入）。
3. 从 manifest 解出密钥（secrets_blob）→ 解密并校验 `state.json.enc` 签名；失败则拒绝加载并提示（防篡改）。
4. 以存档目录路径直接创建 ChunkStore / EventArchive（不复制）。
5. 恢复时钟：`time = max(存档 game_time, archive_max_timestamp)`——防止恢复的世界"时间倒流"（事件归档里可能有比 state 更新的记录）。随后重建日历。
6. 按 seed 重建大陆宏观场（确定性生成，约 30s；continent.bin 缓存命中秒级），tile 从 chunks.db 恢复。
7. 恢复玩家位置（本期）；实体表重建（Issue #25，不发布 entity_born 等事件）。
8. 天气引擎按 seed + 时钟重建调度。
9. 发布 `world_initialized` 事件（含出生点）= 就绪信号；前端据此接入并重新请求 `entity_snapshot` / `player_state`。

世界观处理程序（map/weather/player/entity/terminal）闭包绑定本次
start() 的子系统实例：进程内仅一次 register（一进程一模式，无
replace/unregister 语义）；菜单进程只注册存档处理程序，世界请求
返回 unknown。

## 保存时机汇总

- **脉搏（每 5s）**：state + 事件 flush + chunk flush 一起落盘（统一一致点）。
- **evict 即时**：LRU 淘汰的脏 chunk 立即写回（脉搏之间的安全网）。
- **手动**：玩家主动 `save_snapshot` → 创建 `.ascendsave` 回退点，永久保留。
  快照前同步跑完整 flush + 两库 WAL checkpoint（强一致点，含近期事件）。
- **回滚前自动快照**：读快照/回滚时先自动快照当前状态，保护最新分支。
  自动快照环形保留最近 20 个（+ 当前时间点来源 1 个），手动快照不受限。
- **退出**：排空保存队列做最终脉搏（等价于最后一次完整落盘）。

## 快照血缘（时间线分叉）

`<world_id>/lineage.json` 记录世界的快照血缘（时间线分叉元数据，
世界级元数据，不随快照打包——快照依赖世界内血缘提供父子上下文）。
文件为签名包装结构（HMAC 复用世界 sign_key，与 state.json.enc 同钥、
同威胁级别：防直读/防手贱，不防推导——见 crypto.py）：

```
{data: {live_origin: <快照文件名 | "">,      # 当前活目录来源（回滚目标 / "" = 世界初始）
        snapshots: {<快照文件名>: {
            parent: <派生来源文件名 | "">,   # 创建时活目录来源
            game_time: <tick>, saved_at: <真实时刻>,
            seq: <单调递增序号>}}},          # 权威排序键（创建顺序，回滚后游戏时间
                                             # 倒退不受影响）
 sig: <HMAC-SHA256(sign_key, canonical(data)) 的 urlsafe base64>}
```

- `seq` 是排序的**单一事实来源**：编号、时间线链内串链、兄弟排序统一使用，
  `saved_at`/`game_time` 仅作展示；`stat.mtime` 不参与排序。
- **严格模式**：无有效签名的血缘一律视为损坏（不兼容历史无签名格式，
  不信任任何无法验签的内容）；血缘不可验签时 prune 不做任何淘汰
  （宁缺勿删：空血缘下按文件名序淘汰会误删最近记录、反向对账会误删
  全部文件）。

### 快照删除（单一原语）

删除统一走原语 `remove_snapshots(world_id, files)`（删除集由调用方
计算——单点删除 / 分支裁剪 / 保留策略淘汰都是同一结构变换），文件
删除容忍缺失（磁盘可能已丢，血缘必须自洽）：

- **血缘重接**：被删节点的每个存活子节点 parent 上溯为「最近存活
  祖先」（从被删节点沿原 parent 链回溯，第一个仍在血缘中的节点，
  找不到则 `""`），保证持久化恒满足「parent ∈ 存活集 or ''」且无环。
- **live_origin 可删**：`live_origin` 指向被删节点时沿同一规则回退
  到最近存活祖先（`""` = 世界初始），不拒绝删除。
- **seq 保留空洞**：不重编号——seq 是创建序号，重排会破坏其它已存
  档会话的编号事实；前端编号为位置序号 i+1，对空洞免疫。
- **范围计算**：单点删除 = `{node}`（后代重接）；分支裁剪 =
  `{node} ∪ 后代`（BFS，含自动保护点）；保留策略淘汰 = 满足保留
  规则的最老集合。子树删除无"重挂"语义。

### 前端交互

- 点击快照节点 = 选中并弹出操作面板：「进入存档点」（回滚，直接
  执行）、「删除存档点」（单点，后代重接）、「删除分支」——仅当
  节点有后代时显示（子树含自动保护点）；再次点击同一节点或点击
  空白处关闭面板。
- 删除为危险操作：面板内删除项点击后弹出**模态确认弹窗**（说明
  删除影响：单点删除子节点重接 / 分支裁剪含自动保护点），「删除」
  确认执行，「取消」/ 点弹窗外 / Esc 关闭；live 节点是当前活目录
  （来源），不可删除，点击直接进入世界。存档行（整个世界）的
  删除同样走确认弹窗（删除存档及其全部快照），两次点击确认
  模式已废弃。
- 删除完成后刷新存档列表并**重建保持时间线展开**（不收起时间轴）；
  仅当展开的世界行本身被删除时才收起。

## 协议（状态通道 request-response）

```
save_list 请求 → {payload: {worlds: [
    {world_id, name, seed, game_time, play_duration_sec, saved_at,
     snapshot_count, latest_snapshot_at, format_version}, ...],
    snapshots: [{world_id, file, name?, saved_at, parent, game_time,
                 seq}]}}    # 供存档选择页；血缘字段驱动时间线分叉视图

save_create {name, seed?, gen_params?} → 创建新世界存档位（seed=0/缺省在创建时随机定案；
                                      gen_params 为创建世界流程的调参产出（Issue #8）：
                                      land_ratio/width_km/height_km，范围契约见 manifest.py，
                                      随档定案与 seed 同权重；名称全集合唯一，重名拒绝）
save_snapshot {world_id, name?}    → 手动创建回退点，返回快照文件名
save_snapshot_delete {world_id, snapshot, recursive?} → 删除快照
                                       （recursive=false 单点删除后代重接；
                                         true 分支裁剪节点+后代），
                                       返回 {deleted: [文件名]}
save_rename {world_id, name}       → 重命名（名称唯一；与自身同名允许）
save_delete {world_id}             → 删除世界（连带快照），需确认
save_export {world_id}             → 复制世界为新的存档位（Issue #14 "复制存档"；
                                      副本自动追加"副本"后缀保持名称唯一；
                                      快照逐个改绑副本 ID——副本自包含，
                                      预览/回滚不依赖原世界；任一快照
                                      损坏即整体失败）
```

进入世界 / 回滚不走请求通道（进程模型重构）：前端停菜单进程、以
`run_server --world-id <id> [--snapshot <file>]` 拉起世界进程——
world_id 加载活目录；snapshot 回滚（新进程启动时先自动快照当前
活目录分支再展开，保护语义不变）。

全部为世界外元操作：不产生历史、不进因果图。

## 与相邻 Issue 的关系

- **#25 实体持久化**：被本 Issue 阻塞。存档目录结构、`entities.json.enc` 格式、读档语义（不发布 entity_born）由本设计确定，实现在 #25 落地。
- **#14 存档选择页面**：被本 Issue 阻塞。`save_list` / `save_create` / `save_rename` / `save_delete` / `save_export` 为其接口。
- **#8 开始游戏流程**：创建世界经多步调参（`map_preview` 实时地形预览）→ `save_create`（seed + gen_params 随档定案）→ 停菜单进程、以 `--world-id` 拉起世界进程 → world_loading 进度页（`world_progress` 阶段广播驱动进度）→ `world_initialized` 进入主世界。存档选择页「新建游戏」同样进入该流程。

## 未来优化（本期不做）

- **增量备份**：快照仅打包与上次不同的文件/DB 差异，降低大世界快照成本。
- **SQLCipher**：若 DB 级真加密成为需求，替换明文 SQLite（牺牲实时增量写兼容性）。
- **存档版本迁移**：`format_version` 已预留，schema 变更时实现逐版本迁移。
- **用户密码派生**：如需强防读取（非"防君子"），改为 PBKDF2 用户密码派生密钥。
