# 世界树 — 技术

世界树（`ascend/world_tree/`）是连接所有模块的骨干。模块 A 发布事件时不关心模块 B 是否在监听，订阅者按 event_type 匹配接收。

## 模块结构

```
ascend/world_tree/
├── __init__.py          # 模块级单例 world_tree，公共 API 导出
├── tree.py              # WorldTree 类（发布/订阅/查询/flush-and-drop/trim/configure/warmup）
├── event.py             # Event / WorldEvent / LocationFilter / AffectedParty，空间索引公共函数
├── affected.py          # AffectedParty dataclass
├── scope.py             # SubscriptionScope：订阅凭证统一收集/撤销（模块销毁时一次回收）
├── graph.py             # EventGraph 事件关系有向图
├── archive.py           # EventArchive SQLite 归档
└── schema.sqlite.sql    # 归档 DDL（events、event_entities、event_edges）
```

`SubscriptionScope`：订阅方把 `subscribe` 返回的退订凭证交给作用域统一保管，
`close()` 一次撤销全部（幂等，析构兜底）。WeatherEngine / GameCalendar /
EventBridge 的订阅都经 scope 管理，模块不再自行维护成对的退订代码。
`ascend/lifecycle.py` 的 `LifecycleStack` 同理，用于 GameEngine 装配/拆卸
（start 登记逆操作，stop 按逆序回滚）。

## 事件数据结构

```
Event {
  id: UUID hex (自动生成),
  timestamp: float (游戏秒),
  location: (chunk_x, chunk_y, tile_x?, tile_y?),   // 层内平面坐标
  layer_id: int (默认 0, 0=地表, 负数=地下层),     // Z 轴层标识，正交于 location

  initiator_type: "system" | "npc" | "player",
  initiator_id: string,
  affected: [AffectedParty],     // {entity_id, role: "subject"|"witness"|"recipient"}

  event_type: string,            // "weather_change" "npc_action" "observation" ...
  weight: int (默认 1),           // trim 优先级，1=普通 3=重要 5=关键
  data: dict[str, Any],          // 事件类型特定的内容，JSON 可序列化

  // 事件图关系
  caused_by: [EventID],          // 因果上游
  observes: EventID | None,      // 观测引用（仅观测事件）
  co_participants: [EntityID],   // 共享参与方
}
```

`layer_id` 是离散的 Z 轴层标识（0=地表，-1=浅洞，-2=深洞），不是连续坐标。`location` 保持层内平面坐标——层是正交维度，单独字段表达。这样事件引擎保持 2D 逻辑，跨层交互用两个 2D 事件联动而非 3D 事件。详见地图生成文档的 Z 轴设计。

## 事件契约（data 字段）

每个产生事件的模块用 **事件契约类** 声明自己发布的 data 结构：一个 `WorldEvent`
子类 dataclass，**字段即 data 键，类型即 data 值类型**，`event_type` 由类属性
声明（发布时不再重复写字符串）。契约类紧挨发布代码所在模块（如 `time/events.py`、
`weather/events.py`、`entity/events.py`）。注意：WorldClock 不发布 WorldTree
事件——高频 tick 信号走 `on_tick` / `on_skip` 直接回调，不经过事件总线
（见时间系统文档）。

```python
# time/events.py — 日历事件契约
@dataclass
class DayChange(WorldEvent):
    event_type: ClassVar[str] = "day_change"
    day: int
    previous_day: int
    elapsed_days: int
    day_change_count: int
    skipped_days: int
```

```python
# entity/events.py — 实体事件契约
@dataclass
class EntityBorn(WorldEvent):
    event_type: ClassVar[str] = "entity_born"
    entity_id: str
    entity_type: str
    controller: str
    position: tuple      # as_dict() 输出 list（JSON 形状）
    layer_id: int
    x: int
    y: int
```

- **发布**：各模块的 `_publish(...)` helper 取 `ev.event_type` + `ev.as_dict()`
  （`as_dict()` = `asdict()` 后 tuple 递归转 list，保证 data 与广播/归档的
  JSON 形状一致）。
- **事件类型唯一性**：契约测试对全部事件类断言 `event_type` 全局唯一非空。
- **扩展新事件**：新增一个 `WorldEvent` 子类（字段即契约）+ 发布处实例化 +
  契约测试样本加一行。无注册表、无运行时校验——契约由 dataclass 字段本身
  声明，构造时类型强制。

### 关键事件类型

| 事件类型 | 发布者 | 触发时机 | weight |
|---------|--------|---------|--------|
| `minute_change` | GameCalendar | 分钟变更时 | — |
| `hour_change` | GameCalendar | 整点变更时 | — |
| `day_end` | GameCalendar | 每日结束时（day_change 之前） | — |
| `day_change` | GameCalendar | 日期变更时 | — |
| `entity_born` / `entity_died` / `entity_moved` | EntityManager | 实体在虚拟世界的生灭/移动 | — |
| `player_teleported` | PlayerService | 玩家被强制传送时 | — |
| `world_initialized` | GameEngine | 地图生成+出生点+周边区块就绪后 | 5 |
| 天气事件（15 种） | WeatherEngine | 感知类别变化、降水、极端天气等 | — |

`world_initialized` 携带 `world_id`、`seed`、`birth_chunk`、`loaded_chunks` 数，weight=5（高优先级，trim 时存活更久）。各系统可订阅它做初始化（群体生成、生态播种等——当前无实际订阅者）。

## 世界树核心设计

### WorldTree 类

`WorldTree` 是事件系统的核心类。模块级单例 `world_tree` 通过 `from ascend.world_tree import world_tree` 获取。

```
WorldTree
├── _event_log: list[Event]               热数据（内存）
├── _id_index: dict[str, Event]           ID → Event O(1) 查找
├── _entity_index: dict[str, list[Event]] 实体索引（按时间有序，二分定位）
├── _spatial_index: dict[tuple[int,int,int,int,int], set[Event]] 空间索引（layer+chunk+sub-cell 五元组分桶）
├── _graph: EventGraph                    因果有向图
├── _archive: EventArchive | None         冷数据（SQLite，含边表）
├── _lock: threading.RLock                线程安全
├── _publish_count / _trim_count / _flush_count  运行统计
└── _async_executor: ThreadPoolExecutor   subscribe_async 线程池
```

### 发布流程

```text
publish(event):
    锁内: append → _event_log                O(1)
          更新 _id_index                     O(1)
          更新 _entity_index                 O(A) A=受影响方数
          更新 _spatial_index                O(1)
          _graph.add_event                   O(R) R=关系边数
          抓取订阅者快照
    锁外: _dispatch(event, callbacks)
    量级护栏: len > max_memory_events → trim 到 max//2
           增量清理索引（O(T)，T=被移除事件数）

archive_pending()（保存脉搏，flush-and-drop）:
    锁内: 摘取全部缓冲 + 清空内存/索引/因果图（原子）
    锁外: INSERT OR IGNORE 批量写归档（不占总线锁）
    锁内: 推进水位（cutoff = 本次归档最大 tick + 1）
```

### 分发通道

| 方法 | 执行线程 | 阻塞 publish | 适用场景 |
|------|---------|-------------|---------|
| `subscribe` | publish 调用线程 | 是 | 内存操作（状态更新、计数） |
| `subscribe_async` | 线程池 | 否 | 文件 I/O、网络 I/O |

`subscribe` 返回一个 `unsubscribe()` 函数。`"*"` 通配所有事件类型。

### 线程安全

- 所有公共读写方法由 `threading.RLock` 保护
- `publish()` 在锁内完成写入和订阅者快照，锁外执行回调
- 回调异常被 `try/except` 隔离，单个回调失败不影响其他订阅者
- 查询方法（`get_events_in_range` 等）持锁读取，确保一致性
- 归档查询在锁外执行（SQLite 有独立的并发控制），不占总线锁

### 事件契约保证

发布不校验 data 字段——data 结构由各模块的 `WorldEvent` 契约类在构造时
强制（字段即 data 键，类型即值类型），契约测试断言发布路径的 data 键与
契约字段集合一致、全部事件 `event_type` 全局唯一且可 JSON 序列化。
无运行时注册表、无反射校验开销。

## 事件存储

### 内存层（热数据）

活跃窗口内的事件全部在内存中。`_event_log` 只追加不修改。内存是**写缓冲 +
热窗口**：事件发布后先入内存（订阅分发、索引查询都命中内存），每个保存脉搏由
`archive_pending()` 整体归档并清空（flush-and-drop，见归档层），因此内存中任一
时刻只保留"未落盘缓冲"，不会无限增长。

**实体索引**：`dict[str, list[Event]]`，entity_id → 事件列表（按时间有序）。查询使用 `bisect` 直接在 Event 对象上定位，O(log E + K)。

**空间索引**：`dict[tuple[int,int,int,int,int], set[Event]]`，key = `(layer_id, chunk_x, chunk_y, sub_cx, sub_cy)`。chunk 内按 16×16 tile 细分为 sub-cell（共 13×13 格），tile 坐标通过 `tile // SUB_CELL_SIZE` 映射到 sub-cell 索引。`layer_id` 在前，不同层落入不同桶，天然隔离。

`get_events_in_region` 支持两层过滤：chunk 级（`center_chunk + radius`，必选）+ 可选的 sub-cell 级（`center_tile + sub_radius`）。`center_tile` 传入后仅中心 chunk 的匹配 sub-cell 被查询，周边 chunk 不受限制。`get_events_in_region` 限定单层查询（默认 `layer_id=0` 地表），跨层查询不在此支持——层间隔离是设计意图。

公共辅助函数（`ascend/world_tree/event.py`）：

- `spatial_key(layer_id, chunk_x, chunk_y, tile_x?, tile_y?)` → 5-tuple — 计算空间索引键，供 EntityManager 等外部模块使用。tile 为 None 时 sub-cell 回退到 0。
- `sub_cell_range(tile_x, tile_y, sub_radius)` → `((scx_lo, scx_hi), (scy_lo, scy_hi))` — 给定 tile 和半径，返回 sub-cell 索引闭区间，边界自动钳制在 `[0, SUB_CELLS-1]`。
- `SUB_CELL_SIZE: int = 16` / `SUB_CELLS: int = 13` — sub-cell 粒度和每维度数量。

`EntityManager` 的空间索引同步升级为 5 元组（通过 `spatial_key()`），`in_region()` 新增 `center_tile` / `sub_radius` 参数支持 tile 级精筛。`Entity.layer_chunk` 属性已移除（索引键改由 `spatial_key()` 直接计算）。

### 归档层（冷数据）

通过 `configure(archive_path="save/events.db")` 或构造参数启用 SQLite 归档。
**归档是事件的事实源（权威）**，内存只是写缓冲 + 热窗口。

**存储**：三张表 — `events`（事件体，含 `layer_id` 列）、`event_entities`（实体索引）、`event_edges`（因果边）。`events` 表有 `(layer_id, chunk_x, chunk_y)` 复合索引支持层内区域查询。事件体 + 实体引用 + 边关系一同写入。`INSERT OR IGNORE` 保证幂等（主键 `events.id`、`event_entities(event_id, entity_id)`、`event_edges(from_id, to_id, relation_type)`）。新建库执行 `schema.sqlite.sql`，无旧库迁移路径（旧 schema 库写入会失败）。

**持久化时机（flush-and-drop）**：每个保存脉搏（`SAVE_PULSE_INTERVAL`，默认 5s）
由 `archive_pending()` 把**全部内存缓冲**归档进 SQLite，然后从内存/索引/因果图
移除，并推进水位（cutoff = 本次归档最大 tick + 1）。

水位仅用于合并判定（非严格时间分区）：归档中事件 timestamp 均 < 水位，
查询 start < 水位时归档可能存在重叠事件；同 tick 迟到事件（flush 后
才发布、ts < 水位）留在内存缓冲，重叠由 `_merge_archived` 按 ID 去重兜底。
崩溃丢失 = 最多一个脉搏间隔的未落盘缓冲；已提交行由 WAL 保障。

**查询**：查询方法自动合并内存和归档结果——`_should_merge_archive` 按水位判断
（start < 水位 → 合并归档），`_merge_archived` 按事件 ID 去重后排序，对调用方
透明，不重复不遗漏。

### 事件图 + 预热

`EventGraph` 维护邻接表（正向 `from_id → [(to_id, rel)]` + 反向 `to_id → [(from_id, rel)]`）。trim 时会移除被归档节点，但边已写入 `event_edges` 表。

`warmup_graph(max_events)` 启动时从归档边表批量恢复最近事件的边到内存，避免重启后因果追溯频繁走 SQLite 懒加载。

被移除节点的边仍可通过 `get_causal_chain(lookup=...)` 按需从归档恢复。

## 生命周期

| 方法 | 说明 |
|------|------|
| `configure(*, archive_path?, max_memory_events?)` | 运行期配置归档和内存上限 |
| `archive_pending()` | 归档全部内存缓冲并清空（保存脉搏调用；幂等） |
| `warmup_graph(max_events=10000)` | 从归档边表预热因果图到内存 |
| `await_async()` | 等待所有异步回调完成（退出前调用） |
| `clear()` | 清空全部状态（仅测试） |

### trim（量级护栏，自动）

事件持久化以保存脉搏的 `archive_pending()` 为主；trim 仅在单个脉搏内事件量
超过 `max_memory_events`（默认 10 万）时兜底，防止极端突发撑爆内存：
`len > max_memory_events` → trim 到 `max//2`。

- **权重分层**：weight=1 首次即移除，weight=3 存活 2 次 trim，weight=5 存活 4 次
- **增量清理**：只移除被归档事件在索引中的条目，O(T)，T=移除数
- **边表写入**：trim 时边关系写入 `event_edges`，供 warmup 恢复

## 使用方式

```python
from ascend.world_tree import world_tree, Event, AffectedParty

# 配置（GameEngine.start() 中调用）
world_tree.configure(archive_path="save/events.db", max_memory_events=100_000)
world_tree.warmup_graph(max_events=10_000)

# 发布
world_tree.publish(Event(
    timestamp=game_time,
    location=(chunk_x, chunk_y, None, None),  # 层内平面坐标
    layer_id=0,                                # 0=地表（默认）
    initiator_type="system",
    initiator_id="weather_system",
    affected=[AffectedParty("world", "subject")],
    event_type="weather_change",
    data={"from": "clear", "to": "rain"},
))

# 订阅
unsub = world_tree.subscribe("weather_change", handle_weather)
# 异步订阅（I/O 密集场景）
world_tree.subscribe_async("weather_change", handle_weather_slow)

# 查询
events = world_tree.get_entity_events("npc_1", start_time, end_time)
chain = world_tree.graph.get_causal_chain(event_id)

# 统计
stats = world_tree.stats
```

## NPC 时间线索引（待实现）

每个 NPC 维护一个事件引用列表，指向世界事件日志。是索引而非副本——共享事件只有一个存储位置，所有参与者通过索引指向它。

索引结构：`{event_id, relevance_score, memory_depth}`

- `relevance_score`：对 NPC 的重要性，由注意层计算
- `memory_depth`：随世界时间衰减，深度低于阈值的事件从活跃索引中移除（归档而非删除）

当前通过 `get_entity_events()` 直接查询实体参与的所有事件，NPC 时间线索引待心智系统实现后补充。

## 事件升级（未实现）

个人事件 → 聚落事件 → 世界事件的升级判定不在世界树内部，而由相应的上层系统（群体社会、心智系统）判定后，生成新的事件，通过 `caused_by` 引用原始事件。

世界树只提供查询支持——"这个个人事件当前影响了多少人？"——供上层做升级判定。

各系统的 `tick()` 返回事件列表，世界树负责存储和路由。本身不生成事件。
该推演框架尚无实现（见时间系统文档的"快进"部分）。
